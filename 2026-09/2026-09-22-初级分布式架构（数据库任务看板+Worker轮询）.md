### 目前状况

之前自己的工作大多是单机链路式的，稍微复杂点的可能会用http请求调用一下远端服务器的ComfyUI。现在工作开始涉及到把工具写成更多人使用的平台，开始接触到初级的分布式架构。

以前的工作模式：
```
自己启动脚本 → 调用 ComfyUI → 等待 → 得到图片
```

现在的平台模式：
```
用户在前端提交需求
        ↓
API 接单，把任务写进数据库
        ↓
Worker 从数据库领取任务
        ↓
调用生图模型 / ComfyUI 等工具
        ↓
把进度、结果或错误写回数据库
        ↓
前端查询数据库中的结果，展示给用户
```

|角色|通俗理解|主要职责|
|---|---|---|
|前端|下单和查进度的窗口|提交需求、展示结果|
|API|接单员|检查请求、登记任务、提供查询|
|数据库|共享订单本|保存任务、排队状态、领取记录和结果|
|Worker|干活的工人|领取任务，调用模型或工作流，写回结果|

### 回到目前的架构中

在目前数据库作为作为API和Worker中间的桥梁，会发现一些问题。

>如果用传统的 SQL 数据库（如 SQLite / MySQL / PostgreSQL），Worker 去“轮询（Polling）”确实是必然发生的，因为传统数据库本质上只是一个“静态的数据存取盘”，它确实不会主动给 Worker 派发任务。
  这也正是为什么工业界**坚决不推荐用数据库当任务看板/队列**的根本原因。

#### 数据库作为任务看板的冲突
1. 无效请求（CPU 与 磁盘 I/O 浪费）： 如果现在半夜没有人画图，10 个 Worker 依然会每秒发 10 次 SQL 语句去查数据库。一天下来就是几十万次无意义的查询，把数据库的 CPU 和磁盘 I/O 白白磨损掉。

2. 延迟与吞吐量的矛盾：

	想让响应变快？ Worker 就得加快轮询频率（比如 0.1 秒查一次），数据库立刻被打爆。

	想保护数据库？ 只能降低轮询频率（比如 5 秒查一次），那用户提交任务后就要硬生生多等 5 秒，体验极差。

3. 高并发下的“死锁与锁竞争”： 当 100 个 Worker 同时去执行 UPDATE tasks SET status='processing' WHERE id=1 抢单时，数据库内部会产生严重的锁冲突（Lock Contention），性能急速下降。
